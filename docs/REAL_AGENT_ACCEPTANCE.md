## Changes and execution boundary

- The existing three-tool OpenAI Responses planner remains. Generic `/api/research` exposes all three allowlisted tools with `tool_choice=required`, so the model must select a tool and structured plan. Fixed screening/interval endpoints remain compatible and identify their selection as `FIXED_ENDPOINT` in REAL_LLM mode.
- Accepted interval model bounds and row selection are used only after comparison with the independent original-request interpretation. Model field omissions, invented filters, changed bounds/rows and wrong tools refuse execution. The named Huang selection is restricted to the existing published rows 1-3 and checked against loaded source metadata and comparison grouping.
- Added narrow support for the exact A/B natural wording, `degrees Celsius`, a nominal point interpretation of `around`, and conditional in-source screening semantics for `promising`. Unknown appended clauses still fail closed, including model-omitted humidity/lifetime. This is bounded English, not arbitrary language understanding or fuzzy temperature tolerance.
- Added typed `ExecutionTrace` and typed generic API responses. The trace carries original question, runtime/model/response identity, selected tool, validated arguments, scientific result, audit verdict and grounded explanation. Offline traces cannot claim model identity or model-selected tools. Top-level and scientific-result trace/arguments are checked for consistency.
- Added a compact research-agent panel with three questions, explicit runtime, source-row controls, execution/export and failure state. The original screening and Temperature Decision Explorer also expose backend execution traces. Existing graphs, formula audit, source evidence and deterministic workflows remain.
- Safe provider metadata records requested/returned model identity, actual response ID, receipt timestamp and numeric token counts when available. Raw prompts, provider messages, unknown usage fields and response bodies are not shown. Provider refusal prose on an independently covered request is a typed `MODEL_PLAN_CONFLICT` with prose withheld; actual user constraints remain in independent coverage.

Scientific values, source DOIs, units, regime selection and explanation templates come entirely from validated backend results. The LLM does not generate the displayed scientific arithmetic/citations, fetch URLs or execute code. No additional explanation/model turn is used. The generic model plan is material to tool selection and accepted arguments, rather than a paraphrase of an already completed answer.

[Official OpenAI strict function-calling documentation](https://developers.openai.com/api/docs/guides/function-calling#strict-mode) was fetched October 21: every function schema explicitly uses strict mode, forbids additional properties and lists all properties as required, with nullable fields where absent. ## Live execution gate and limits

Normal browser regression explicitly clears OPENAI_API_KEY/OXYPROOF_LLM_MODEL in both its launcher and isolated test server. Its missing-configuration test first confirms NOT_CONFIGURED before requesting REAL_LLM. This prevents ordinary regression from incurring model charges if the owner's normal environment is later configured. These are genuine local HTTP/browser checks in an intentionally unconfigured test server, not live provider acceptance. The separate application service and acceptance CLI retain the owner's own environment.

Default execution is safe and makes **zero model requests**, even if credentials later exist:

```sh
uv run --offline --no-sync python scripts/accept_real_agent.py
```

Only after the owner provides supported environment configuration **and explicitly authorizes billable use**, run:

```sh
uv run --offline --no-sync python scripts/accept_real_agent.py --live --authorize-paid-calls
```

If using an ignored .env, explicitly pass `--env-file .env` to `uv run`; never paste credentials into chat, reports or tracked files. Without both live/authorization flags or usable configuration, all live cases remain NOT_RUN. The runner attempts **at most three requests**, one per mandatory scenario, with **no retries**, below the owner's six-request cap. Each adapter call has a 25-second transport timeout (5-second connection), 64 KiB response bound, 2000 output-token cap and exactly one allowlisted tool. No model is selected automatically.

VERIFIED is assigned only if actual provider executions for all three scenarios pass independent numeric/source/constraint checks. Errors remain errors; no mock/offline substitution is labelled real. A future live run may still reveal model/schema/API incompatibilities despite the passing contracts. Use the remaining allowed requests only with owner authorization and a concrete diagnostic need.
